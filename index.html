WordPress Contact Form Not Sending Emails? Diagnostic Checklist

Your form looks fine. Someone submits it. Nothing useful arrives in your inbox. This guide walks through the checks that most often separate a real delivery failure from a configuration mistake — without assuming every WordPress or email problem has the same cause.

1. Confirm the submission actually succeeds

Before blaming email, prove the form completed its request.

  • Submit a real test with a unique phrase in the message body (e.g. TEST-2026-10-03-A).
  • Watch for a success message, redirect, or thank-you page — not just a button click.
  • Open browser DevTools → Network: look for the form POST (or AJAX call). Note status code (200/302 vs 4xx/5xx).
  • If the request fails or never fires, the problem is the form front-end / validation / JS — not mail delivery yet.
  • Check the form plugin’s entries / submissions log (if it has one). A saved entry with no email is a different problem from no entry at all.

If the form already reports success (or saves an entry) but the notification never arrives, follow the focused guide: WordPress contact form says sent but no email arrives.

2. Check spam and junk folders

Many “not sending” reports are “sent but filtered.”

  • Search the recipient inbox (and any shared/team inbox) for your unique test phrase.
  • Check Spam / Junk / Quarantine — including Google Workspace / Microsoft 365 quarantine if you use them.
  • Check filters/rules that auto-archive or forward form mail.
  • If mail arrives in spam, note From, Reply-To, and subject — weak SPF/DKIM or a mismatched From domain often causes this.

3. Verify recipient / admin email

Wrong destination is common after site migrations or staff changes.

  • In the form plugin, confirm the notification “To” address is current and typed correctly.
  • Compare against Settings → General → Administration Email Address (they are not always the same).
  • If notifications go to a role or dynamic field, confirm that field is populated on submit.
  • Send a plain WordPress test (or host panel mail test) to the same address to separate “form config” from “mailbox rejects mail.”

4. SMTP and mail delivery

Default PHP mail() on shared hosting is unreliable. Many hosts throttle or drop it.

  • Ask: does this site use an SMTP plugin or transactional provider (e.g. authenticated SMTP, API mailer)?
  • If SMTP is configured, open its send log / last error. Failed auth, TLS, or daily limits show up there.
  • Confirm the From address uses a domain you control and that SPF/DKIM align for that sending service.
  • Test sending from a different path (hosting “send test email,” or a simple SMTP test) to the same recipient.
  • Do not assume every missing email is an SMTP problem — only treat it as one after submission success and correct recipient are confirmed.

5. Form plugin notifications

Contact Form 7, WPForms, Gravity Forms, Fluent Forms, and others each store mail settings differently.

  • Confirm the admin notification is enabled (not only a user auto-reply).
  • Check Mail / Notification tabs for empty To, broken mail-tags, or conditional logic that skips send.
  • If there is an auto-reply to the visitor, test whether that arrives while admin mail does not (or the reverse) — it narrows the fault.
  • After plugin or site updates, re-open the form and save once; some setups need a re-save after migrations.
  • Disable one recent add-on (spam service, CRM hook, webhook) temporarily if sends stopped after it was installed — then re-test once.

6. Caching and security interference

Caches and firewalls can break POST, nonces, or AJAX without an obvious UI error.

  • Purge page cache / CDN cache for the contact page; retest in a private window.
  • Exclude the contact page (and admin-ajax.php / form endpoints) from full-page cache if your cache plugin allows it.
  • Check security / WAF / bot protection logs for blocked form POSTs (especially after adding CAPTCHA or rate limits).
  • Temporarily disable one layer (cache plugin or firewall rule — not everything at once) and retest with the same unique phrase.
  • If the site is behind Cloudflare or similar, review Bot Fight / Managed Challenges on the form URL.

7. Mobile and browser test

Some failures only appear on phone layouts or specific browsers.

  • Repeat the same unique-phrase test on a phone (real device) and on desktop.
  • Try a second browser, and one private/incognito window (extensions can block scripts).
  • On mobile, confirm required fields, consent checkboxes, and sticky headers are not covering the submit control.
  • If desktop works and mobile fails (or vice versa), note viewport, browser, and whether the Network request differs.

8. Confirmation / thank-you path

A “broken form” report sometimes means the visitor never saw confirmation — even when mail worked.

  • Confirm what should happen on success: inline message, redirect URL, or both.
  • Open the thank-you / success URL directly; check for 404, wrong language version, or cached stale page.
  • If redirect depends on a query parameter or form ID, verify it still matches after a redesign.
  • For multi-step or booking-style forms, confirm the final step is the one that triggers notification — earlier steps may only save drafts.

9. Test evidence to record

Clear notes turn a vague “emails don’t work” into something fixable.

  • Date/time (with timezone), page URL, device, browser.
  • Unique message phrase used in the test.
  • Whether the UI showed success; Network status for the submit request.
  • Whether an entry appeared in the form plugin log.
  • Inboxes checked (including spam/quarantine) and whether mail arrived.
  • SMTP/plugin log snippet or error string, if any.
  • What you changed between tests (one change at a time).

10. When it becomes multi-step rather than a simple fix

A single wrong recipient, disabled notification, or spam-folder hit is often a short fix. It is usually not a one-shot tweak when several of these are true:

  • Submission succeeds and entries save, but mail is inconsistent across recipients or time.
  • SMTP, DNS (SPF/DKIM), and plugin notifications all need coordinated changes.
  • The path spans multiple steps, conditional fields, CRM/webhooks, or separate confirmation pages.
  • Caching/CDN/WAF changes fix one device but break another.
  • You cannot reproduce reliably enough to verify a single change.

At that point, treat it as an enquiry-path repair problem: map the full path, fix the agreed defect, and re-test with recorded evidence — not a guess-and-hope inbox refresh.
